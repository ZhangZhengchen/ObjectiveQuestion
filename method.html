Blackbox and whitebox test selection

Blackbox test selection uses the specification; whitebox selection also uses implementation structure. Expected behaviour must still be justified by the specification.

Retained judgment: For each supplied testing decision, determine whether selection uses only the specification or also implementation structure, and whether its expected check remains contract-conforming.

Source: Reading 3: Testing · Blackbox and Whitebox Testing

The contract for find(arr, val) requires val in arr and guarantees an index i with arr[i] = val. The implementation has a special branch for arrays longer than 20 and caches repeated calls (internally reuses a result). Match each proposal to its selection basis and check quality. Choices may be reused.

Choices

C1Specification-only selection; contract-conforming check
C2Specification-only selection; nonconforming check
C3Implementation-informed selection; contract-conforming check
C4Implementation-informed selection; nonconforming check

Rows to match

R1Test find([4,9],9); check arr[i]=9.
R2To exercise the long-array branch, use 21 elements with 9 twice; check arr[i]=9.
R3To exercise the cache, repeat find([9,9],9); require the second call to return the first call’s index.
R4From the contract alone, test find([9,9],9); require index 0.

Whole-item exact match; no partial credit. Options may be reused.

Reference answer and explanation

R1 → C1 (Specification-only selection; contract-conforming check); R2 → C3 (Implementation-informed selection; contract-conforming check); R3 → C4 (Implementation-informed selection; nonconforming check); R4 → C2 (Specification-only selection; nonconforming check)

R1 uses only contract information and checks the guaranteed relationship. R2 targets an implementation branch but accepts either matching index. R3 targets the cache but incorrectly requires the first result when either duplicate index is permitted. R4 uses no implementation fact, but its expected index is not guaranteed.

Five-stage design record

Stage 1: assessment target and observable evidence

Distinguish which proposed testing decisions are based on specifications versus implementation structure, and whether expectations remain contract-conforming.

Several strategy-to-testing-basis correspondences. Recognize that a test chosen from implementation knowledge must still use specification-justified expectations.

Stage 2: scenario and open task

A team tests find(arr, val). Its contract requires val to occur in arr and guarantees an index i where arr[i] equals val. The code uses a special branch for arrays longer than 20 and caches repeated calls.

As the test reviewer, write a brief recommendation to the developers. Propose three legal tests: one derived only from the contract, one exercising the long-array branch, and one exercising the cache. For each, state the input, expected check, and whether its selection is blackbox or whitebox. Explain why every check remains contract-conforming when val occurs more than once.

GRASPS

Goal: Design and justify tests by separating specification-based selection from implementation-informed selection.

Role: Test reviewer

Audience: Development team

Situation: The team needs tests that cover stated behavior and implementation structures without demanding an unspecified result.

Product: A concise three-test recommendation

Success criteria

  • All calls use arrays containing val.
  • Each test identifies its selection basis.
  • The whitebox tests exercise the stated branch or cache.
  • Each check accepts any returned index whose element equals val.

Stage 5: response design

Matching directly assesses the focal SE04 distinction while keeping SE08 as the constraint on expected checks. Four rows can map to four reusable combined categories without requiring a single prescribed test design or disclosing the target mapping.

Performance not retained

  • Independent production of test inputs and assertions
  • Independent construction of tests for all three purposes
  • Written defense of each expected check
